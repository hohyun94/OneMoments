# 키 백업·기기 복구

기기 키를 잃으면 서버에 남은 암호문을 영원히 복호화할 수 없다. 이 기능은 **복구 암호**로 기기 키를 암호화해 서버에 보관하고, 새 브라우저에서 **같은 기기 ID**로 복구해 기존 이력을 이어서 읽게 한다.

## 1. 보안 모델

| 항목 | 내용 |
|---|---|
| 암호화 위치 | 클라이언트(브라우저). 서버는 불투명 블롭만 저장 |
| 키 유도 | PBKDF2-SHA256, 600,000회, 16바이트 salt |
| 암호화 | AES-256-GCM, 12바이트 nonce, ciphertext‖tag |
| 복구 증명 | 서버가 발급한 일회용 챌린지 nonce에 **기기 Ed25519 키로 서명** |
| 세션 | 복구 성공 시 해당 기기의 **기존 세션 전부 폐기** 후 새 세션 발급 |
| 서버가 아는 것 | 백업 블롭(암호문), 기기 공개키, 복구 시각 |
| 서버가 모르는 것 | 복구 암호, 기기 개인키, 평문 |

> 복구 암호는 서버로 전송되지 않는다. 대신 암호화된 블롭을 username으로 조회할 수 있으므로,
> **복구 암호가 약하면 오프라인 대입 공격**에 노출된다. 10자 이상 + 높은 엔트로피를 권장한다.

## 2. 흐름

### 백업 (기존 기기)

1. 기기 관리 → **키 백업**에서 복구 암호(10자 이상)와 확인 입력
2. 브라우저가 `{backend, deviceId, 공개키, 개인키(pkcs8/raw)}`를 JSON으로 만들고 PBKDF2+AES-GCM으로 암호화
3. `PUT /api/auth/backup` `{blob}` — 서버는 크기만 확인하고 저장(기기당 1개, 갱신 시 덮어씀)
4. `GET /api/auth/backup`으로 마지막 백업 시각 확인

### 복구 (새 브라우저)

1. 로그인 화면 → **복구** 탭 → 아이디 + 복구 암호
2. `POST /api/auth/recovery/lookup` `{username}` → 암호화된 블롭
3. 클라이언트가 복구 암호로 복호화 → 기기 키 복원
4. `POST /api/auth/recovery/challenge` `{deviceId}` → `{challengeId, challenge}` (5분 유효, 1회용)
5. 클라이언트가 `recover:<challenge>`를 Ed25519로 서명
6. `POST /api/auth/recover` `{deviceId, challengeId, signature}` → 서버가 서명 검증 후 세션 발급
7. 새 브라우저가 **같은 deviceId**로 세션을 받으므로, 그 기기 앞으로 감싼 기존 키 봉투를 그대로 복호화할 수 있다.

## 3. API

| 메서드 | 경로 | 인증 | 설명 |
|---|---|---|---|
| PUT | `/api/auth/backup` | 세션+CSRF | 내 기기 백업 저장/갱신 |
| GET | `/api/auth/backup` | 세션 | 내 기기 백업 조회 |
| POST | `/api/auth/recovery/lookup` | 없음(레이트리밋) | username의 최신 백업 블롭 |
| POST | `/api/auth/recovery/challenge` | 없음(레이트리밋) | 기기 복구 챌린지 발급 |
| POST | `/api/auth/recover` | 없음(레이트리밋) | 서명 검증 후 세션 발급 |

오류: `BACKUP_NOT_FOUND`(404), `RECOVERY_UNAVAILABLE`(404, 폐기/없는 기기),
`RECOVERY_CHALLENGE_INVALID`(400, 만료/재사용), `UNAUTHORIZED`(401, 서명 불일치).

## 4. 한계

- **기기당 백업 1개**: 여러 기기를 쓰면 각 기기에서 백업해야 하며, 복구 조회는 최신 백업을 사용한다.
  다른 기기의 백업을 선택하는 UI는 후속 과제다.
- **폐기된 기기는 복구 불가**: 기기 폐기는 “이 키를 더는 신뢰하지 않음”을 뜻하므로 복구를 막는다.
- **복구 암호 분실 = 복구 불가**: 서버·운영자도 키를 복구할 수 없다.
- **이전 버전 키**: 백업 기능 이전에 만든 non-extractable 키는 내보낼 수 없어 백업이 실패한다.
  새 기기에서 다시 로그인해 새 키를 만들고 백업해야 한다.
- **XSS tradeoff**: 백업을 위해 브라우저의 private `CryptoKey`를 extractable로 보관한다.
  엄격한 CSP·서드파티 스크립트 금지로 완화하지만, XSS가 발생하면 키가 노출될 수 있다.
  (대안: 가입 시 복구 암호를 필수로 받고 즉시 암호화한 뒤 non-extractable로 재가져오기 — 후속 설계)
- **복구는 기기 단위**: 같은 계정의 다른 기기로 이력이 자동 이전되지는 않는다.

## 5. 검증

- 서버 테스트: 백업 저장/조회, 챌린지 1회용, 잘못된 서명 거부, 폐기 기기 거부, 크기 제한,
  복구 후 기존 세션 무효 + 이력 복호화
- 클라이언트 테스트: 백엔드별 백업 왕복, 잘못된 복구 암호/변조 블롭 거부
- E2E: 백업 저장 → 새 브라우저에서 복구 → 대화 이력 복호화 → 기기 1개 확인
